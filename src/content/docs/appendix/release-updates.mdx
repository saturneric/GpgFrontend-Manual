## In Short, for Everyday Users

- **Your keys and settings are not touched.** An update only replaces the
  app.
- **Nothing installs by itself.** When an update exists, a small red dot
  appears on **Help** > **Check for Updates** and in the status bar. Its
  tooltip says **A newer version is available**. Open **Help** > **Check for
  Updates** and click **Download**. This opens the right file for your
  system, or the [Downloads](/overview/downloads/) page.
- **You choose the version.** The check offers fix releases of your own
  series. When your series is old, it also recommends the current release,
  and you pick one. See
  [Which Updates the App Offers](/appendix/version-policy/#which-updates-the-app-offers).
- **The update check is your choice.** It only runs by itself if you agreed
  during setup, at most once a day, and sends no name or account. To change
  it, go to **Edit** > **Settings** > **Updates** (on macOS:
  **Preferences**).
- **Every file is signed.** The key for stable releases is never stored on a
  server. To check a download yourself, see
  [Code & Binary Verify](/appendix/code-binary-verify/).

The rest of this page is for experts.

## Architecture

| Component             | Role                                                                                                                     | Trust boundary                                                                    |
| :-------------------- | :----------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------- |
| Public repository     | Source of truth for code, build recipe, release policy and the trust root.                                               | Tags for stable releases are signed by the maintainer.                            |
| GitHub Actions        | Builds every platform and records provenance with Sigstore. A separate hourly job mirrors stable releases to GitHub Releases. | No build job has `contents: write`. Only the mirror job does, and it can only write this repository's GitHub releases. No job can write to the release store. |
| Staging bucket        | Holds builds exactly as CI signed them.                                                                                  | Private. Never served to users.                                                   |
| Signing host          | Verifies and publishes nightlies, betas and release candidates. Re-checks stable releases before it lists them. Signs the update index. | Holds the index key only. Never holds the OpenPGP, Authenticode or root keys. |
| Maintainer's machine  | Runs the offline stable stage: OpenPGP and Authenticode signing, then the upload of the stable release.                  | Keys are not on any server. Authenticode key is on a hardware token.              |
| Root key holders      | Sign the trust root, which says which keys sign what.                                                                    | Kept offline. Two of three root keys must sign.                                   |
| Release store         | Serves published files from `builds.bktus.com` and the index from `update.bktus.com`.                                    | Holds no keys. Objects are immutable once written.                                |
| Client (the app)      | Checks for updates and verifies the signed index against the trust root.                                                 | The trust root and key list are built in.                                         |

## Trust Root and Index Keys

The keys are not hard-coded one by one. A small chain of signed files says
which key may sign what:

1. **The trust root** (`release/root/<N>.root.json`) names the root keys,
   the key that signs the index-keys list (the "G" key), and what the signing
   host must check before it lists a release: the repository and workflow,
   the maintainer's OpenPGP fingerprint and the Authenticode subject. At least
   2 of the 3 root keys must sign it. Each signature is a separate
   `<N>.root.json.<keyid>.minisig` file.
2. **The index-keys list** (`release/index-keys/<V>.json`) names the keys that
   may sign the index. The G key signs it.
3. **The index** is signed by a key on that list.

Rules:

- A new root `N+1` counts only if a threshold of root `N`'s keys **and** a
  threshold of its own keys signed it. Roots are walked one version at a
  time, at most 32 in one check.
- A new root is valid for 2 years, a new index-keys list for 1 year. The
  signing host warns when fewer than 60 days (root) or 30 days (list) are
  left.
- A retired maintainer key or Authenticode subject still counts when a
  release that was already listed is checked again. It never counts for a new
  release.
- The app builds in the newest root and list of the source it was built
  from. It takes newer ones from the update store when the index names them,
  and keeps them.

## Build and Release Pipeline

### CI: Build and Stage

- CI signs and stages only four kinds of push:
  - a push to `main` (a nightly);
  - a push to `release/X.Y` (a beta of series X.Y);
  - a release candidate tag `vX.Y.0-rc.N` (a prerelease of series X.Y, see
    [Release Candidates](#release-candidates));
  - a release tag `vX.Y.Z` (a stable release).

  Pull requests, manual runs and all other tags are built but never signed or
  staged.
- The build jobs hold no secrets. Apple signing (Developer ID, notarization,
  stapling) and Android signing run in separate jobs, in protected
  environments.
- A `provenance` job collects every file and writes `SHA256SUMS.txt`. It signs
  that list keyless with Sigstore `cosign`. The certificate names the
  workflow, the ref and the commit, and the signature is logged in Rekor.
- A `stage` job uploads the build to the private staging bucket. A release
  candidate is staged beside its series' betas.
- No job in `build.yml` publishes downloads. It has no `contents: write`, so
  it cannot create a GitHub release, and it cannot write to the release store.
  There is one exception, for Android: a separate job uploads every build it
  stages to the internal testing track of Google Play. Stable releases, betas
  and release candidates go to the app `com.bktus.gpgfrontend`; nightlies go
  to `com.bktus.gpgfrontend.nightly`.

### GitHub Releases Mirror

GitHub Releases is a mirror, filled after a release is published, never
before. The workflow `.github/workflows/github-release.yml` runs every hour
(and by hand):

- It reads the signed update index from the public servers, the same way the
  app does, and checks it against the trust root.
- For each stable release in the index, it makes the GitHub release match:
  the files with their maintainer `.sig` signatures, and the signed release
  notes.
- It checks every file against the index and its signature before it uploads
  it. So a mirrored file is the same as the one the update check offers.
- Its job is the only one with `contents: write`. That token can only write
  this repository's releases. It holds no signing key.

Betas, release candidates and nightlies are not mirrored.

### Which Builds Are Separate Apps

| Build                   | Built as | App name               | Keys and settings                       |
| :---------------------- | :------- | :--------------------- | :-------------------------------------- |
| Stable release          | release  | GpgFrontend            | the normal ones                         |
| Beta (`release/X.Y`)    | release  | GpgFrontend            | the same as the stable release          |
| Release candidate       | release  | GpgFrontend            | the same as the stable release          |
| Nightly (`main`)        | nightly  | GpgFrontend Testing    | its own, kept apart                     |

A nightly is a separate product everywhere. On Windows it has its own
UpgradeCode, install folder, registry key and shortcut, and installs beside a
stable release. On Android it is its own app.

### Promotion on the Signing Host

The signing host runs `gfrelease promote`. It promotes builds of `main`, of
`release/X.Y` and of release candidate tags, and of nothing else. For each
ref it takes only the newest staged build. Before it publishes anything, it
checks:

1. The Sigstore bundle names this project's `build.yml`, at exactly the ref
   and commit the build claims.
2. Every file matches the signed `SHA256SUMS.txt`, and no extra file is
   present.
3. The version is what git says that commit is, not merely what the build
   claimed. A final version is refused, and so is a version outside the
   branch's series.
4. For a release candidate: the tag points to that commit, the commit is on
   `release/X.Y`, and the series has no release yet.

It then copies the files, CI's manifest and its Sigstore bundle to
`nightly/<version>/`, writes the build's descriptor (its list of files) last,
and a commit marker after it. Nothing is signed at this step.

### Stable Release: the Offline Stage

CI only stages a tag build. A stable release reaches users only through
`gfrelease stable`, which the maintainer runs by hand:

<Steps>

1. **Fetch** the staged build of tag `vX.Y.Z`.
2. **Verify** before signing: the Sigstore bundle names this workflow at that
   tag and commit, every file matches the signed list, the tag is signed by a
   maintainer key and points at that commit, and git calls it that version.
3. **Authenticode:** sign the Windows installers with the certificate on its
   hardware token. The timestamp request is the only network call in this
   step.
4. **OpenPGP:** write a detached binary `.sig` for every final file, a final
   `SHA256SUMS.txt` with its own `.sig`, and signed release notes.
5. **Upload** everything to `releases/<version>/`, the descriptor last.

</Steps>

On its next round, the signing host admits the release. It checks again,
against the keys the trust root pins: the signed tag and its commit, the
maintainer-signed file list against the descriptor, every file's `.sig`, the
Sigstore build hashes, the Authenticode signature and its timestamp, and the
signed notes. Only then does it list the release in the index.

The app relies on the signed index alone. The index names each descriptor by
its hash, and the descriptor names each file by its hash. The `.sig` files are
for people who check a download by hand.

### Imported Releases

`gfrelease import` brought GitHub releases from 2.1.5 onward into the release
store. Each file keeps its original maintainer `.sig`, byte for byte. Nothing
was signed again. The signing host checks each imported file against its
`.sig` once, then lists the release. Releases before 2.1.5 were signed with
keys that are no longer pinned, so they stay on [GitHub][github-releases]
only.

## Versioning

### Version Numbers Come From Git Tags

No version number is written into the build files. CMake derives it from
`git describe` (`cmake/GitVersion.cmake`). The version string is written and
sorted by the rules of Semantic Versioning 2.0.0. Only the format follows
those rules. What the numbers mean is a separate matter, explained in
[Version Policy](/appendix/version-policy/).

| Build                                          | Version                    |
| :--------------------------------------------- | :------------------------- |
| On a release tag `vX.Y.Z`                      | `X.Y.Z`                    |
| On a release candidate tag `vX.Y.0-rc.N`       | `X.Y.0-rc.N`               |
| N commits after the base tag `vX.Y.0-alpha.0`  | `X.Y.0-alpha.N+g<sha>`     |
| N commits after `vX.Y.0-rc.K`                  | `X.Y.0-rc.K.dev.N+g<sha>`  |
| N commits after `vX.Y.Z`, on `release/X.Y`     | `X.Y.(Z+1)-alpha.N+g<sha>` |
| N commits after `vX.Y.Z`, on any other branch  | `X.(Y+1).0-alpha.N+g<sha>` |

- A **feature release** is tagged `vX.Y.0`. A **fix release** is tagged
  `vX.Y.Z` with Z above 0, on `release/X.Y`.
- A **release candidate** is tagged `vX.Y.0-rc.N`. It is a prerelease, never
  a release. Only `X.Y.0` can have one, and only before `vX.Y.0` exists. CI
  does not publish an rc tag of any other shape, and refuses one for a series
  that is already released.
- Old tags such as `v2.2.0-beta.1` are still read, so old commits keep their
  versions. No new beta tags are made.
- The base tag is set on `main` by `scripts/release/cut.sh`, when the branch
  for the series before it is cut. From then on, `main` counts from it. A
  base tag only marks a starting point. It is never a release.

A version string tells you exactly where a build comes from. The `<sha>` part
is the commit it was built from. CI refuses a build of `main` that would not
sort above every release, and a build of `release/X.Y` that would not sort
above every release of series X.Y.

### Release Candidates

A new series is cut at its first release candidate:

<Steps>

1. The maintainer tags `vX.Y.0-rc.1` on `main`, and edits
   `release/policy.toml`: X.Y becomes `stable`, X.(Y+1) `mainline`.
2. `scripts/release/cut.sh X.Y` creates `release/X.Y` at that tag, commits
   the policy, and sets the base tag `vX.(Y+1).0-alpha.0` on `main`.
3. Further candidates (`vX.Y.0-rc.2`, …) are tagged on `release/X.Y`. Each is
   built, staged, promoted and listed like a beta.
4. When `vX.Y.0` is tagged and released, the series is an ordinary stable
   series. Its candidates are no longer listed.

</Steps>

A series released without a candidate is cut at `vX.Y.0` instead.

### Release Lines

`release/policy.toml` is the single place where each series' status is set.
The support table in `SECURITY.md`, the update index and the order check in
CI all read it.

| Status     | Meaning                                                                                                                        |
| :--------- | :----------------------------------------------------------------------------------------------------------------------------- |
| `mainline` | Under development on `main`. Its builds are the nightlies.                                                                     |
| `stable`   | A released series that still gets fixes on `release/X.Y`, whose builds are its betas. Several series can be stable at once.  |
| `legacy`   | An older series that gets security fixes until its `eol` date. Its users are offered the series its successor chain ends at. |
| `eol`      | No more fixes. Its users are offered only the series its successor chain ends at.                                            |

A stable series is shown as a **prerelease** in the index while it has a
release candidate and no release yet. Nobody sets this by hand.

At the time of writing: 2.3 is mainline, 2.2 is stable, 2.1 is legacy until
2027-12-31 (the last series that builds with Qt 5), and 2.0 and 1.x are end of
life. The file also sets the minimum platform for the mainline and stable
series (Windows build, macOS version, glibc, Android API). The app only
recommends a series that this system can run.

#### Successor Chains

A legacy or end-of-life series names a `successor`. The app follows it, and
goes on through every successor that is itself legacy or end of life, until
it reaches a stable series. That series' newest release is the one it
recommends. A stable series is never sent anywhere, even if it names a
successor.

`policy.py check` refuses a chain that loops, steps back to an older series,
or ends anywhere but at a stable series. It warns when a successor is not a
stable series itself: apps older than v2.2.5 read only one step of the chain.
So when a series becomes legacy, point every successor at a stable series
directly.

#### When a Legacy Series Reaches Its End Date

Nothing changes on its own. After the `eol` date, `policy.py check` warns
that the date has passed. The maintainer then sets the series to `eol`, and
the next signed index says so. The app never compares the date itself. It
only reads the status from the index:

- The notice in **Check for Updates** changes from "The X series gets
  security fixes only, until …" to "The X series no longer gets fixes."
- Fix releases of that series are no longer offered. Only the current release
  is, where it runs.
- The app keeps working. Its keys and settings are not touched, nothing is
  removed, and published files stay published.

## Update Checking

The **Help** > **Check for Updates** dialog and the background check live in
the `m_ver_check` module.

### Consent and Schedule

- One switch controls automatic checks: the setting
  `network/prohibit_update_check`. The setup wizard asks with **Check for
  updates on startup** (unticked by default). Afterwards it is changed under
  **Updates** > **Update Checking** > **Check for updates automatically, once
  a day.** in Settings. Changes apply without a restart.
- Until the wizard has run, there are no automatic checks.
- When the app has started, and then every hour, it looks whether a check is
  due. A check is due when the last good result is older than 24 hours. A
  failed check is retried at the next hourly look.
- **Check now** and **Check again** in the dialog always go online, even with
  automatic checks off, because the user asked.
- **Also offer beta versions** (unticked by default) is under **Updates** in
  Settings, for release builds only. It adds betas and release candidates to
  the offers. Without it, the dialog only mentions a newer beta: **A newer
  beta, …, is available**. Nightly builds follow their own channel and do not
  show it.

### Endpoints and Data Sent

- Every build asks the project's own servers, not GitHub. From
  `https://update.bktus.com/gpgfrontend/v1/` it fetches `index.json` and
  `index.json.minisig`. When the index names a newer root or index-keys list,
  it also fetches `root/<N>.root.json` with each root key's
  `.minisig`, and `index-keys/<V>.json` with its `.minisig`.
- From `https://builds.bktus.com/gpgfrontend/` it fetches the descriptor and
  release notes of each version it offers. Last, it asks for
  `commits/<commit>`, to learn whether its own build was published. Your
  build commit is in that URL. Your version number is not sent.
- Every request is a plain GET with a fixed, generic browser User-Agent
  string. There is one string per system family (Windows, macOS, Linux), set
  at build time. No user ID or machine ID is sent. Your real OS version,
  architecture and package type are only used locally, to pick a file.
- As with any HTTPS request, the server sees your IP address.

### The Signed Update Index

It lists:

- each series with its status, end-of-life date, successor, platforms,
  latest release, beta and release candidate;
- the `stable`, `beta`, `prerelease` and `nightly` channels;
- withdrawn versions, and a hashed descriptor for each release;
- the root and index-keys versions it is signed under, a `serial`, a
  `generated_at` time and an `expires` time.

The client checks:

- The trust root and index-keys list, as described in
  [Trust Root and Index Keys](#trust-root-and-index-keys). An expired root or
  list blocks the index.
- The index's minisign (Ed25519) signature, with libsodium, by a key on the
  index-keys list. The signed trusted comment must read
  `product=gpgfrontend serial=<n>`, and the serial must match the file.
- An index more than one day past `expires` is refused. So is an index that
  claims to be valid for more than 60 days. The signing host signs it for 14
  days, and signs it again before it runs out.
- The highest accepted serial is stored for each index key, and any lower
  serial under that key is refused. This stops a stale copy or an attacker
  from replaying an old index.
- Each descriptor and release notes must match the hashes the index gives for
  them. One that does not costs only that version's download link or notes.
- If nothing valid comes back, the result is "unknown", never a verdict. The
  dialog shows **Couldn't reach the update server** or **Update information
  couldn't be verified**, together with the last known result if there is
  one.

Every build uses this index: stable releases, betas, release candidates and
nightlies.

### What Gets Offered

| Build                                        | What it is offered                                                                                     |
| :------------------------------------------- | :----------------------------------------------------------------------------------------------------- |
| Release build, series `stable`               | The newest release of its own series. Never another series.                                           |
| Release build, series `legacy`               | The newest release of its own series, and the newest release of the series its successor chain ends at. |
| Release build, series `eol`                  | Only the newest release of the series its successor chain ends at.                                    |
| With **Also offer beta versions**            | Also its own series' beta (not for `eol`), and the release candidate of the newest prerelease series. |
| Release candidate build                      | Newer candidates of its own series, then its release.                                                 |
| Nightly of `main`                            | The single version in the `nightly` channel.                                                          |
| Nightly of `release/X.Y` (a local build)     | Its series' beta. With none, it is offered nothing: **This is a release branch build**.              |

- The successor and the release candidate are offered only where this system
  meets that series' platform minimum. Otherwise the notice says why.
- When more than one version is offered, the dialog lets the user choose
  under **Offered**. The successor is picked by default and marked
  **(recommended)**. Without one, the series' own release is picked. A beta or
  release candidate is never picked by default.
- **Download** opens the exact file for this platform and package type, taken
  from the verified descriptor of the chosen version. When no file fits, it
  opens the Downloads page.
- Installs that a package manager or store keeps up to date (distribution
  packages, MSIX) get no **Download** button. They show **Updates for this
  build come from …**.
- A background check never opens a window. A new offer sets a badge on
  **Help** > **Check for Updates** and a red dot in the status bar with
  **A newer version is available**. Each kind of offer (own series,
  successor, beta, release candidate) is remembered as seen on its own, so a
  new one of any kind is announced. For nightlies, the badge stays quiet for
  24 hours after an update was seen.

<Aside type="note" title="New in v2.2.5">

Older apps offered only their own series' releases, and their beta when
asked for. A legacy or end-of-life series only showed a notice, which named
its direct successor.

</Aside>

### In-Place AppImage Updates

Only an AppImage of the nightly app (**GpgFrontend Testing**) can update
itself. The dialog offers **Install update** only when `$APPIMAGE` is an
absolute path to a regular, writable file (not a symlink) in a writable
folder.

1. The new file is downloaded to a temporary file next to the old one, with a
   size limit.
2. Its size and SHA-256 must match the signed descriptor, or it is deleted.
3. Only then does it replace the old file, keeping its permissions.
4. The app restarts only when the user clicks **Restart now**. It relaunches
   from the `.AppImage` file, not from its mount point.

There is no separate signature on the AppImage itself. Its trust comes from
the signed index, which pins the descriptor's hash, which pins the file's
hash.

### Builds Without an Update Check

- **Flatpak and Mac App Store:** the module is not built. Updates come from
  the store, and the wizard does not show the option.
- **Android:** the Android app is built without modules, so there is no
  update check in the app.
- **Builds without the trust files:** a build made without `release/root` and
  `release/index-keys` cannot verify anything. The dialog says **Updates
  aren't available for this build** and does not check.

## Security Properties

- **Separation of duties.** CI can build but not publish. The signing host
  can publish but holds no stable signing key and no root key. A stable
  release needs the maintainer's offline stage.
- **Keys off servers.** The OpenPGP, Authenticode and root keys are never on
  a server. A compromised CI runner, signing host or release store cannot
  produce a valid stable signature, and cannot make the app trust a new
  index key.
- **Threshold-signed trust root.** Changing which keys sign the index needs a
  new index-keys list from the offline G key. Changing the G key or the root
  keys needs two of the three root keys.
- **Provenance checked before publishing.** Every signer verifies the
  Sigstore bundle against the exact workflow, ref and commit, and asks git
  for the version itself.
- **Immutable objects.** Published files are never replaced.
- **Monotonic versions.** CI refuses builds that would sort below an existing
  release. The Windows installer refuses downgrades.
- **Anti-rollback for the index.** Serials only grow, and the index expires.

## Known Limitations

- Releases before 2.1.5 are only on GitHub. The update index does not list
  them.
- The update check reveals the build commit to the server it asks. The
  commit also tells the server which version is running.
- Apps older than v2.2.5 follow only one step of a successor chain.

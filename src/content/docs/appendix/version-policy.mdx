Every copy of GpgFrontend has a version number, like `v2.3.1`. The number
tells you two things: which feature release you have, and how many rounds of
fixes it has had since.

<Aside type="note" title="Changed in v2.2.5">

Before v2.2.5, the last number counted feature releases. Since v2.2.5, it
counts only fix releases. New features now raise the middle number. See
[How It Used to Work](#how-it-used-to-work). The maintainer explains why in
["GpgFrontend's New Version Model and Release Mechanism"][blog-version-model].

</Aside>

## What the Numbers Mean

A version number has three parts. Here is `v2.3.1`:

| Part      | Name            | What it means                                                         |
| :-------- | :-------------- | :-------------------------------------------------------------------- |
| **2**.3.1 | Generation      | The app was rebuilt from the ground up. This has happened once.       |
| 2.**3**.1 | Feature release | New features. A new one comes out about every two months.             |
| 2.3.**1** | Fix release     | Fixes for that feature release. It comes out whenever one is needed. |

The first two numbers together are called the **series**. In `v2.3.1`, the
series is **2.3**. The update check and the rest of this manual use that word.

## Feature Releases Bring New Things

Each feature release raises the middle number: `v2.3.0`, then `v2.4.0`, and
so on. It brings new features and changes, and it is where bigger work lands.

Some feature releases also take the app in a new direction. Two real examples:

- **2.1** moved the app onto a modern toolkit and let you choose which copy of
  GnuPG to use.
- **2.2** added a second engine, rPGP, so GnuPG was no longer the only way to do
  the work. This is why the app is now described as having a "dual-engine core".

A change of direction is a decision the project makes first, and usually
writes down before the code exists. Most feature releases do not change
direction. They add features along the same road.

## Fix Releases Keep a Release Stable

A fix release raises only the last number: `v2.3.0`, then `v2.3.1`, then
`v2.3.2`.

- It is mostly fixes, including urgent ones (hot fixes). It may add a few
  small features, never large ones. Big features wait for the next feature
  release.
- It comes out as soon as it is ready. It does not wait for the next feature
  release.
- A feature release can get several fix releases.

So a fix release is a safe update. Taking it keeps your version stable.

## Why Not Semantic Versioning

You may have heard of **Semantic Versioning**. It is a common set of rules for
numbering software.

Those rules were written for code libraries: software that other programmers
build their own programs on top of. The numbers answer one question: _did
something break for the programmers using this?_

GpgFrontend is an app you use, not a library programmers build on. Its
version numbers look the same, and they sort the same way. But they answer a
different question: _is this new features, or fixes for what you already
have?_

## Stable, Beta, Release Candidate and Nightly

Not every build is meant for everyday use:

<CardGrid>
<Card title="Stable" icon="approve-check-circle">

A normal release, like `v2.3.1`. This is the one you want.

</Card>
<Card title="Beta" icon="magnifier">

A test build of the next fix release of one series. Its version looks like
`2.3.2-alpha.3`. It runs as the normal app and uses the same keys and
settings as your stable copy, so back up your keys first.

</Card>
<Card title="Release candidate" icon="rocket">

An early test version of the next feature release, like `2.4.0-rc.1`. It is a
beta, never a stable release. There is one only while that feature release
is not out yet. It uses the same keys and settings as your stable copy.

</Card>
<Card title="Nightly" icon="warning">

An automatic test build, made from the newest code. It can be broken. Its
version looks like `2.4.0-alpha.120`. It runs as a separate app, **GpgFrontend
Testing**, with its own keys and settings.

</Card>
</CardGrid>

To be told about betas and release candidates, open **Edit** > **Settings** >
**Updates** (on macOS: **Preferences**) in a stable release, and tick **Also
offer beta versions**. It is off unless you tick it.

<Aside type="note" title="Changed in v2.2.5">

A beta used to be a tagged early version of a new series, like
`v2.2.0-beta.1`, and it ran as **GpgFrontend Testing**. Now a beta is an
untagged test build of the next fix release, and it runs as the normal app.
The early version of a new series is now a release candidate. The beta
setting used to be in the **Check for Updates** window. It is now under
**Settings** > **Updates**.

</Aside>

See [Downloads](/overview/downloads/) for where to get each kind of build,
and the [FAQ](/overview/faq/) for more about nightly builds.

## Which Updates the App Offers

The update check looks at the series you have. What it offers depends on how
that series is doing:

| Your series    | What it means                         | What the app offers                                     |
| :------------- | :------------------------------------ | :------------------------------------------------------ |
| Stable         | It still gets fixes.                  | Fix releases of your series.                            |
| Legacy         | It gets security fixes only, for now. | Fix releases of your series, and the current release.   |
| End of life    | It gets nothing any more.             | Only the current release.                               |

The **current release** is the newest release of the series that legacy
users are meant to move to. The app follows the chain from series to series
until it finds one that is still stable. It recommends it only if your system
can run it.

More than one series can be stable at the same time. Then each one gets its
own fixes, and none of them points you to another series. That only starts
once a series becomes legacy.

<Aside type="note" title="New in v2.2.5">

When more than one version is offered, you choose which one to download. To
do so:

<Steps>

1. Open **Help** > **Check for Updates**.
2. Under **Offered**, pick a version. The current release is marked
   **(recommended)** and is picked for you. Betas and release candidates are
   never picked for you.
3. Click **Download**.

</Steps>

Before v2.2.5, the app offered only fix releases of your own series, and
showed a notice when your series was old.

</Aside>

The update check never moves you to another series by itself. Nothing
installs without you. To learn how the check works and how to turn it off,
see [How Releases and Updates Work](/appendix/release-updates/#update-checking).

## When a Series Gets Old

When a newer series comes out, the older one does not stop right away:

1. For a while it can stay **stable** next to the new one, and keep getting
   fixes.
2. Then it becomes **legacy**. It gets security fixes only, up to a set date.
   The app recommends the current release, next to your fixes.
3. After that date it reaches **end of life**. It gets no fixes at all. The
   app only offers the current release.

Your copy keeps working the whole time. Your keys and settings are not
touched, and nothing is removed. Moving to the newer series is up to you.

The `2.1.x` series is legacy until the end of 2027.

The project looks after at most three series at the same time. That is the
maintainer's own rule, not something the app enforces.

## The Story So Far

| Series  | What it was about                                                                             |
| :------ | :-------------------------------------------------------------------------------------------- |
| **1.0** | Being real software. Getting the app packaged and signed so people could actually install it. |
| **1.1** | Working with files, through a built-in file browser.                                          |
| **1.2** | Getting your encrypted text out to other people, and starting translations.                   |
| **2.0** | A rebuilt core. Everything inside was rewritten.                                              |
| **2.1** | A modern toolkit, more control over GnuPG, and a long run of steady, careful releases.        |
| **2.2** | Two engines instead of one, plus support for newer OpenPGP standards.                         |
| **2.3** | The first feature release under the new numbering.                                            |

The 2.0 release notes show that the number was picked on purpose:

> "Since the core part of the code and the organizational structure are different
> from the previous version, **the version number of this version of GpgFrontend
> starts from v2**."

## How It Used to Work

Up to v2.2.4, the middle number changed only when the app took a new
direction. The last number counted the releases in that direction, and each
one could be big.

For example, `v2.2.1` to `v2.2.2` looks like a tiny step. That release added
[Profiles](/advanced/profiles/), portable profile files you can carry around,
Instant Messaging tokens, a new key list, and a rebuilt settings window.
`v2.2.3` was just as big. It added sending and reading email, signed modules,
temporary profiles, and key databases that change without a restart.

From v2.2.5 on, that is no longer the case. `v2.2.5` and later `2.2.x`
versions are fix releases, and new features arrive in `v2.3.0`.

Why the change? A release came out about every two months. A bug found just
after one had to wait for the next, and that next one also brought new
features. Most people want a stable app, and many cannot build it
themselves. Now a fix can go out to each series on its own, as a fix
release, without new features attached.

<Aside type="note" title="How to tell what changed">

Read the release notes. When the app offers you an update, **Help** >
**Check for Updates** shows the notes of that version. The notes of every
version are on the [Release Notes](/overview/release-notes/) page. They say
what actually changed in each version.

</Aside>

## Why the Generation Number Stays Small

GpgFrontend has been going since 2021, and the first number has changed once.
The middle number now moves with every feature release. The first one moves
only when the app is rebuilt from the ground up.

That is a deliberate choice, described in the maintainer's article
["The Past and Present of GpgFrontend"][blog-history]:

> "I firmly believe that **steady progress is more valuable than blind
> innovation**."
